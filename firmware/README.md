# firmware — аппаратные клиенты «Дорога на восток»

Это PlatformIO-проект с прошивками для аппаратных клиентов игры. На старте здесь
живёт один клиент — для LilyGO TTGO T-Display v1.1, — но структура рассчитана
на то, чтобы рядом без боли появлялись клиенты для других плат.

## Структура

```
firmware/
├── platformio.ini          # одна секция [env:*] на каждое устройство
├── boards/                 # кастомные манифесты плат для PlatformIO
│   └── lilygo-t-display-v11.json
├── include/                # общие заголовки (auto-included PlatformIO)
│   ├── game_data_types.h   # контракт структур контента с генератором ассетов
│   ├── generated/          # запечённые ассеты и контент (коммитятся в репозиторий)
│   ├── road_east_version.h
│   └── local_secrets.example.h
├── lib/                    # приватные библиотеки проекта (см. lib/README)
├── src/
│   ├── common/             # портируемый код: игра, рендер, UI (без Arduino/TFT)
│   │   ├── canvas.{h,cpp}         # RGB565-поверхность: примитивы, спрайты, клип
│   │   ├── text_render.{h,cpp}    # UTF-8 растровый текст, два шрифта, перенос слов
│   │   ├── game_assets.{h,cpp}    # доступ к сгенерированным таблицам
│   │   ├── game.{h,cpp}           # состояние и правила (порт js/app.js)
│   │   ├── scene_render.{h,cpp}   # пиксель-арт сцены из data/scenes.json
│   │   └── ui.{h,cpp}             # композиция экранов 240x135
│   └── lilygo_tdisplay/    # точка входа и платформо-зависимый код клиента
│       └── main.cpp        # дисплей, кнопки, кадровый цикл
└── test/                   # PlatformIO unit-tests
```

Граница проведена так: `src/common/` рисует в обычный `road_east::gfx::Canvas`
(указатель на буфер RGB565) и ничего не знает ни про Arduino, ни про TFT_eSPI.
Клиент устройства владеет буфером, опрашивает кнопки и раз в кадр выталкивает
буфер на панель. Портировать игру на другую плату — значит написать заново
только `main.cpp`.

Один общий `platformio.ini` со множеством environment-ов — это идиоматичный
PlatformIO-способ держать несколько целей в одном репозитории: общий код
шарится через `src/common/` и `lib/`, а каждое устройство получает свой
`build_src_filter`, свой `board`, свои `lib_deps` и свои `build_flags`.

## Сборка и прошивка

Требуется установленный [PlatformIO Core](https://docs.platformio.org/en/latest/core/installation/index.html)
(или расширение PlatformIO IDE для VS Code). Из директории `firmware/`:

```bash
# собрать прошивку для LilyGO T-Display (env по умолчанию)
pio run

# залить на подключенную плату
pio run -t upload

# подключиться к serial-консоли
pio device monitor

# собрать конкретное окружение
pio run -e lilygo-t-display
```

## Локальные секреты

Wi-Fi пароли и прочие токены кладём в `include/local_secrets.h`, который
гитом игнорируется. Шаблон лежит рядом — `include/local_secrets.example.h`,
просто скопируй его и заполни:

```bash
cp include/local_secrets.example.h include/local_secrets.h
```

## Как добавить новое устройство

1. Создай папку `src/<device_id>/` и положи туда минимум `main.cpp`.
2. Если плата нестандартная — добавь её манифест в `boards/`.
3. В `platformio.ini` добавь новую секцию environment по образцу
   `[env:lilygo-t-display]`. Ключевые поля:
   - `platform`, `board` — целевая платформа и плата.
   - `build_src_filter` — обязательно ограничить сборку нужными папками:
     ```ini
     build_src_filter =
         -<*>
         +<common/**>
         +<<device_id>/**>
     ```
   - `lib_deps`, `build_flags` — зависимости и флаги, специфичные для платы.
4. Общий код, который захочется шарить между устройствами, кладём в
   `src/common/` (или, когда модуль вырастет, выносим в `lib/`).

Договорённость: device-specific код **никогда** не дёргается из `src/common/`
напрямую. Общий слой объявляет интерфейс, а каждое устройство реализует
платформо-зависимую часть у себя — это держит шаринг кода честным и
предотвращает скрытые зависимости от одной конкретной железки.

## LilyGO TTGO T-Display v1.1 — пины

| Назначение         | GPIO |
|--------------------|------|
| Кнопка «выбор»     | 0    |
| Кнопка «переключение» | 35 |
| Подсветка дисплея  | 4    |
| TFT MOSI / SCLK    | 19 / 18 |
| TFT CS / DC / RST  | 5 / 16 / 23 |

Прошивка работает в landscape (`setRotation(1)`), экран — 240x135. Кнопки
опрашиваются по фронту (`justPressed`); кнопка на GPIO 35 не имеет внутреннего
pull-up на этой ревизии, поэтому объявлена как `INPUT`, а не `INPUT_PULLUP`.

## Управление

Повторяет схему браузерного прототипа (`setupButton()` в `js/app.js`):
длинным считается удержание от 600 мс.

| Кнопка          | Короткое нажатие      | Удержание           |
|-----------------|-----------------------|---------------------|
| Верхняя (GPIO 35) | листать выборы      | статус и подсказка  |
| Нижняя (GPIO 0)   | подтвердить выбор   | карта маршрута      |

Пока проигрывается переходная сцена, ввод игнорируется. Любое нажатие при
открытом оверлее закрывает его, а на карточке последствий — продолжает игру.
Повторное удержание верхней кнопки на экране статуса возвращает в меню — это
единственный выход из партии на двух кнопках.

## Экран

Экран собран как в PWA, но пересчитан под 240x135 (`src/common/ui.cpp`):
верхняя панель ресурсов, панель отряда шириной 60 px слева, текст события и
список выборов справа. Переходные сцены рисуются 1:1 в своём внутреннем
разрешении 204x115 (те же `SCENE_W`/`SCENE_H`, что и в вебе) и центрируются
на панели.

Текст набирается шрифтом 6x12: при 8x16 в строку помещается 30 символов, и
тексты событий не влезают. Шрифт растрируется в ячейку 7x12 с шагом 6 px —
несколько глифов (`0`, `ы`, `ю`, `щ`) требуют седьмой колонки, и обрезка
превращала их в другие буквы. Генератор падает, если глиф не влезает в ячейку.

## Конвертация ассетов в C++ ресурсы

Графика, шрифты и игровой контент собираются в заголовочные файлы скриптом
[`scripts/build_firmware_assets.py`](../scripts/build_firmware_assets.py).
Он собирает:

- `generated/splash_image.h` — 16-цветный splash из `assets/sprites/splash.png`
  (палитра RGB565 + 4bpp упакованные пиксели).
- `generated/font_8x16.h`, `generated/font_6x12.h` — растровые шрифты с
  печатной ASCII, кириллицей (А-я, Ё/ё) и типографской пунктуацией
  («», –, —, кавычки, …), рендерятся из TTF.
- `generated/sprites_data.h` — спрайт-шиты из `data/sprites.json` в RGB565
  плюс 1bpp маска прозрачности.
- `generated/scenes_data.h` — слои сцен из `data/scenes.json`.
- `generated/events_data.h` — события и выборы из `data/events.json`.

Три последних файла раскладываются по структурам из
[`include/game_data_types.h`](include/game_data_types.h) — это и есть контракт
между генератором и прошивкой. Спрайты и сцены адресуются индексами в порядке
следования ключей в JSON, поэтому порядок ключей значим. Скрипт падает с
внятной ошибкой на неизвестном имени сцены/спрайта, битом `next_id`, размере
PNG, не совпадающем с манифестом, и глифе, не влезающем в ячейку шрифта.

Установка зависимостей и запуск из корня репозитория:

```bash
pip install Pillow
python scripts/build_firmware_assets.py
```

Опции:

```
--splash-png PATH   путь к 16-цветному PNG (по умолчанию assets/sprites/splash.png)
--font-ttf PATH     путь к TTF (по умолчанию C:/Windows/Fonts/consola.ttf)
--data-dir PATH     где лежат events/scenes/sprites.json (по умолчанию data/)
--out-dir PATH      куда писать заголовки (по умолчанию firmware/include/generated/)
```

Сгенерированные заголовки **коммитятся в репозиторий** — обычная сборка
прошивки не требует ни Python, ни Pillow. Перегенерируйте их каждый раз, когда
меняется контент в `data/`, спрайт в `assets/sprites/` или нужно подменить
шрифт.

UTF-8 строки декодируются и отрисовываются через
[`src/common/text_render.{h,cpp}`](src/common/text_render.h) — поддерживаются
ASCII 0x20–0x7E, U+0410..U+044F, Ё/ё и список пунктуации из `FONT_EXTRA`.
Остальные кодпойнты заменяются на пробел; добавлять новые нужно синхронно —
`FONT_EXTRA` в скрипте и `kExtraCodepoints` в `text_render.cpp`, **только в
конец**, иначе поедут индексы уже существующих глифов.
